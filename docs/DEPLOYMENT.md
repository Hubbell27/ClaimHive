# Deploying ClaimHive on AWS

This guide sets up ClaimHive in an AWS account that is covered by a Business
Associate Addendum (BAA). The infrastructure is defined in `infra/terraform`.
CI checks it with `terraform validate` on every push, but it has not yet been
applied to a real account: plan carefully the first time.

**Do not load real patient data until every item in [PILOT_CHECKLIST.md](PILOT_CHECKLIST.md)
is done and `npm run readiness` passes against the deployment.**

## What gets created

| Piece | AWS service | Notes |
|---|---|---|
| Network | VPC, 2 AZs | Public subnets (load balancer, NAT), private (app), isolated (database, no internet route). VPC endpoints for KMS, Secrets Manager, Logs, ECR, S3. Rejected-traffic flow logs |
| Web app + worker | ECS Fargate | One image, three task definitions: `web` (behind the ALB), `worker` (jobs), `migrate` (one-off). Circuit-breaker rollback |
| Database | RDS PostgreSQL 17 | Encrypted (KMS), TLS enforced (`rds.force_ssl`), Multi-AZ, 35-day point-in-time recovery, deletion protection. Statement text is never logged |
| Keys | KMS (3 keys, yearly rotation) | `app` wraps each practice's data key and the platform key; `data` for RDS; `logs` for CloudWatch/SNS/CloudTrail |
| Secrets | Secrets Manager | Database URLs, role passwords, platform key, optional Anthropic key. Values are put in by hand, so they never enter Terraform state |
| Edge | ALB + WAF | TLS 1.2/1.3 only, HTTP → HTTPS, AWS managed rules (common, bad inputs, SQLi, IP reputation) and a per-IP rate limit. Access logs to a private bucket |
| Monitoring | CloudWatch, SNS, CloudTrail | Alarms for 5xx, unhealthy targets, DB CPU/storage and the worker being down. Multi-region CloudTrail with log validation (records every KMS unwrap) |

## 0. Before you start

1. **Accept the AWS BAA** in AWS Artifact for this account. Use only HIPAA-eligible services (everything above is).
2. Pick a region (default `us-east-1`) and a domain, e.g. `app.claimhive.com`.
3. Request an **ACM certificate** for the domain in that region and validate it with DNS.
4. Create an **S3 bucket for Terraform state**: versioned, encrypted, with public access blocked. Then uncomment the `backend "s3"` block in `infra/terraform/versions.tf`.
5. Install Terraform 1.9+, the AWS CLI, Docker and Node 22.

## 1. Create the infrastructure

```bash
cd infra/terraform
cp production.tfvars.example production.tfvars   # fill it in; *.tfvars is git-ignored
terraform init
terraform plan -var-file=production.tfvars -out=plan
terraform apply plan
```

The first apply needs an image tag. Use a placeholder (e.g. `bootstrap`); the
services won't be healthy until step 3. Confirm the SNS email subscription when
it arrives.

## 2. Put the secrets in

Get the values Terraform printed: `terraform output`.

```bash
P=claimhive-production
REGION=us-east-1
HOST=$(terraform output -raw db_endpoint)
OWNER_PW=$(aws secretsmanager get-secret-value --secret-id "$(terraform output -raw db_owner_secret_arn)" --query SecretString --output text | jq -r .password)
APP_PW=$(openssl rand -base64 36 | tr -d '/+=' | head -c 40)
POOL_PW=$(openssl rand -base64 36 | tr -d '/+=' | head -c 40)
TLS="sslmode=verify-full&sslrootcert=/etc/ssl/rds-global-bundle.pem"
put() { aws secretsmanager put-secret-value --region $REGION --secret-id "$P/$1" --secret-string "$2" >/dev/null; }

put APP_DB_PASSWORD "$APP_PW"
put POOL_DB_PASSWORD "$POOL_PW"
put MIGRATION_DATABASE_URL "postgresql://claimhive_owner:$(jq -rn --arg p "$OWNER_PW" '$p|@uri')@$HOST:5432/claimhive?$TLS"
put DATABASE_URL "postgresql://claimhive_app:$APP_PW@$HOST:5432/claimhive?$TLS"
put POOL_DATABASE_URL "postgresql://claimhive_pool:$POOL_PW@$HOST:5432/claimhive?$TLS"

# The platform key (seals staff TOTP secrets): generated by KMS, stored only encrypted.
KMS_KEY_ID=$(terraform output -raw kms_app_key_arn) npx tsx scripts/generate-platform-key.ts > /tmp/pk && put PLATFORM_KEY_WRAPPED "$(cat /tmp/pk)" && rm /tmp/pk
unset OWNER_PW APP_PW POOL_PW
```

**Owner password rotation.** RDS manages and rotates the owner password
(`manage_master_user_password`). After a rotation, update
`MIGRATION_DATABASE_URL` before the next migration.

**AI letters.** Leave them off until the Anthropic BAA is signed. Then put a
value in `$P/ANTHROPIC_API_KEY` and set `enable_ai_letters = true` and
`anthropic_baa = "signed"` in the tfvars. Without them, ClaimHive uses its
standard letters and sends nothing to Anthropic.

## 3. Build, migrate, deploy

Tag every image with the git SHA; the repository refuses to overwrite tags.

```bash
REPO=$(terraform -chdir=infra/terraform output -raw ecr_repository)
SHA=$(git rev-parse --short=12 HEAD)
aws ecr get-login-password | docker login --username AWS --password-stdin "${REPO%%/*}"
docker build -t "$REPO:$SHA" . && docker push "$REPO:$SHA"

# Point the task definitions at the new image.
terraform -chdir=infra/terraform apply -var-file=production.tfvars -var image_tag=$SHA

# Run migrations (and set the role passwords) before the new version takes traffic.
aws ecs run-task --cluster "$(terraform -chdir=infra/terraform output -raw cluster)" --launch-type FARGATE \
  --task-definition claimhive-production-migrate \
  --network-configuration "awsvpcConfiguration={subnets=[$(terraform -chdir=infra/terraform output -json private_subnets | jq -r 'join(",")')],securityGroups=[$(terraform -chdir=infra/terraform output -raw task_security_group)]}"
# Watch /claimhive-production/migrate in CloudWatch Logs until it prints "Role passwords set."
```

ECS then rolls out the web and worker services. The circuit breaker rolls back
automatically if the new tasks fail their health check (`/api/health`).

Point the domain at `app_url_target` with a Route 53 alias or CNAME.

## 4. First staff account and checks

Run one-off commands with an ECS task override: same cluster, network and
`web` task definition, with `command` overridden.

```bash
# Staff admin (not a practice account). The temporary password is printed once, to the task's log.
command=["npm","run","create-admin","--","you@claimhive.com","Your Name"]

# Readiness: every automated check must pass before real data.
command=["npm","run","readiness"]
```

Sign in at `https://<domain>/login` and enroll MFA. Then, in **Admin → Billing**,
set the real default contingency rate. **Admin → Readiness** shows the same
checks as `npm run readiness`, plus the manual items.

## 5. Onboard a pilot practice

1. **Admin → Practices → Create practice** with the owner's email. The owner gets a temporary password (share it out of band, e.g. by phone).
2. The owner signs in, sets a password, enrolls MFA, decides about sharing, then follows **Setup**:
   - letterhead;
   - invite billers;
   - import 12 months of aging, 835s and 837s;
   - open the **12-month report**.
3. Sign the practice's BAA before step 2 (see the checklist).

## Operations

- **Backups:** RDS keeps 35 days of point-in-time recovery; the final snapshot is kept on deletion. Test a restore each quarter (see the checklist).
- **Logs:** app logs hold ids, counts and outcomes only, never PHI (`src/lib/logger.ts`). They're kept 365 days, encrypted with the logs key.
- **Audit:** the application audit log lives in the database (append-only). AWS-level actions, including every KMS decrypt of a practice key, are in CloudTrail.
- **Scaling:** raise `web_count` / `worker_count`. Imports and letters run on the worker, so add workers first.
- **Staging:** apply the same code with `environment = "staging"` and `nat_per_az = false`, in a separate account or at least a separate state file. Never copy production data to staging.
